**仓库二实施计划：Landlock＋seccomp BPF**

建议仓库名：`landlock-sandbox`。

目标：构建类似 Sandlock 路线的独立 Linux 沙箱项目，最终提供可安装、可调用、可验证的 CLI。借鉴 Sandlock 的具体能力范围，在调研和设计阶段明确。

本仓库独立维护代码、文档、任务、测试、CI、版本和发布产物。设计阶段考虑通用 Agent 调用方式，不包含 Jiuwen 适配任务。

**一、任务清单**

| ID | 任务 | 主要交付物 | 完成标准 |
|---|---|---|---|
| B00 | 明确首版范围 | 使用场景、目标平台、权限要求、首版能力和排除项 | 明确需要借鉴 Sandlock 的哪些能力及最终验收目标 |
| B01 | 初始化仓库和协作流程 | README、许可证、AGENTS、任务台账、Issue/PR 模板、基础检查 | 仓库可独立检出，开发与验证入口明确 |
| B02 | 调研参考实现与内核机制 | 固定版本的源码研究、许可证清单、能力与风险记录 | 明确 Landlock、静态 BPF 和候选动态监管能力的边界 |
| B03 | 完成方案设计与评审 | 威胁模型、总体设计、CLI 契约、能力矩阵、测试计划、设计决策记录 | 首版范围、运行条件和关键风险得到明确结论 |
| B04 | 验证关键机制 | 能力探测工具、最小原型、原始实测报告 | 必需机制在目标环境实际生效，失败和受阻原因可区分 |
| B05 | 建立 CLI 和构建骨架 | 命令入口、帮助、版本、配置校验、日志、错误处理、构建脚本 | 用户能安装并运行最小示例，配置错误可明确定位 |
| B06 | 实现最小执行闭环 | 限制安装、命令执行、输出和结果收集 | 文件访问与系统调用正反例通过，安装限制失败时拒绝执行业务 |
| B07 | 实现首版完整能力 | 设计确定的网络、进程及其他功能 | 所有声明能力都有正向、拒绝及不支持用例 |
| B08 | 完善生命周期与 Agent 调用 | 超时、取消、异常退出、后代清理、通用调用示例 | Agent 可调用、获取结果、取消任务并识别失败原因 |
| B09 | 完成安全和平台验证 | 对抗、竞态、故障、生命周期与兼容性报告 | 关键问题闭环，实际保护与发布说明一致 |
| B10 | 完成性能、稳定性和发布流水线 | 分阶段耗时、原始基准、重复/并发测试、CI、打包流程 | 数据可复现，资源残留问题解决，必需检查稳定 |
| B11 | 发布首个版本 | CLI 发布包、校验值、安装说明、示例、兼容矩阵、变更记录 | 新用户能从干净环境完成安装、探测和典型任务 |

推进顺序：B00—B03 先完成；B04 与 B05 可以并行；随后推进 B06—B08；功能达到首版范围后完成 B09—B11。

**二、设计阶段必须回答的问题**

B03 需要形成可评审文档，回答以下问题；当前计划不预先确定实现方式：

- 首版需要哪些文件、网络、进程、IPC 和资源限制能力？
- 静态 BPF 与动态监管分别承担哪些功能？
- 是否需要用户态监管，以及由此引入哪些环境要求和安全风险？
- 如何表达最低内核能力、有效保护与不支持项？
- 如何处理并发、进程身份、FD、取消和异常退出？
- 如何保证业务开始前限制已经生效？
- 开发语言、依赖、构建方式和发布包如何选择？
- 性能预算、清理完成条件和版本发布门槛是什么？

如果首版目标包含动态能力，完成静态原型只能算阶段成果。最终完成标准以 B03 冻结的完整范围为准。

**三、Agent 调用要求**

面向通用 Agent，通过 CLI 完成调用。设计与验证至少覆盖：

| 调用环节 | 要求 |
|---|---|
| 启动 | 支持非交互执行，能传入命令、工作目录、策略和必要环境 |
| 输出 | 能明确区分业务 stdout、stderr 与沙箱自身日志 |
| 结果 | 提供机器可读结果，报告实际保护和不支持原因 |
| 控制 | 明确超时、取消、信号及后代清理的行为 |
| 兼容 | CLI 和结果格式具有明确版本约定 |

具体命令、字段、传输格式和流式事件形式，在 B03 中确定。提供一个不依赖专有 Agent 框架的调用示例。

**四、验证与发布要求**

B09 至少覆盖：

- 文件授权、权限重叠、路径绕过和继承 FD。
- 系统调用限制、架构差异和替代调用入口。
- 首版声明的网络能力及绕过路径。
- 设计涉及的内存、FD、进程身份和通知处理竞态。
- 正常退出、非零退出、超时、取消和启动失败。
- 监管组件故障、调用方退出、后台进程及资源残留。
- 设计中声明支持的真实平台和架构。

分别记录原语可用、限制生效、业务成功和禁止行为被拒绝。PASS、FAIL、BLOCKED 分开统计；严格配置和允许缺失部分保护的配置分别报告。

性能报告包含源码版本、策略、环境、原始样本和失败数。预览版与稳定版分别设置发布条件。

**五、后续会话的进展与提交管理**

在仓库中维护实施计划、设计决策和进度台账。每个任务记录：

```text
任务 ID、状态、交付物、关联提交、
验证方式与结果、阻断原因、下一步
```

任务状态统一为：待办、进行中、受阻、完成。

每完成一个可独立审查的改动，运行相关检查，形成关联任务 ID 的提交并推送远端。设计发生变化时，同步更新决策记录、实现、测试和公开说明。

设置三个检查点：

1. **设计可实施**：B03—B04 完成。
2. **CLI 功能完整**：B06—B08 完成。
3. **版本可发布**：B09—B11 完成。

后续会话从核对仓库和 B00 开始，持续跟踪设计、开发、验证、代码提交及发布进展。关键机制验证完成后，再细化工期。
